## 5. 设计模式分析

### 5.1 声明式配置

**优势**: 平衡调整只需修改SKILL_DEFS配置，无需改动业务逻辑

**示例**: 调整Tesla冷却只需修改cooldown值

### 5.2 策略模式

**casters对象**: 每个塔独立实现，易于扩展

**优势**: 
- 添加新塔只需实现对应cast函数
- 修改单塔不影响其他塔
- 清晰的职责划分

### 5.3 钩子系统

**测试系统无侵入集成**:
- battle.hooks.onSkill注入钩子
- 不修改原始代码
- 易于测试和调试

### 5.4 效果组合

**灵活的增益/减益系统**:
- effects对象统一管理
- 支持多种效果叠加
- 时间管理 (until字段)

## 9. 技术亮点

### 9.1 固定配置突破

**问题**: 随机配置导致33.3%失败率 + ±40%数据波动

**解决方案**: 固定7座塔 (每种各1座)

**效果**: 100%胜率稳定性 + 可靠数据对比

### 9.2 伤害归因系统

**问题**: 无法精确追踪每个技能的实际贡献

**解决方案**: override hitEnemy + _activeSkill标记

**效果**: 精确统计每个技能的伤害贡献

### 9.3 可选链大量使用

**防御式编程**: 避免null引用错误

**示例**: `tower?.skillCooldowns?.[tier]`

### 9.4 特效分离

**fx对象**: 解耦视觉和逻辑

**优势**: 无头模式下特效不执行，提升测试性能
